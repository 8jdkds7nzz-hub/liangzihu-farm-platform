# 工程回归与发布操作卡

本卡承接Q01，覆盖检查器补强、Q02、诊断/需求对照、Q04和Q11工程验证。实际完成与外部阻塞以本轮验收记录为准；配置文件存在不代表GitHub CI已经运行。

## 从独立副本开始

在应用仓库内选一个尚不存在的副本路径，执行：

```sh
git worktree add --detach .local/验证副本 HEAD
cd .local/验证副本
pnpm install --frozen-lockfile
pnpm test:setup
pnpm exec playwright install chromium
pnpm check:core
```

`test:setup`只新建自有Docker测试容器、agri_test和随机凭据；不会创建或重置原开发库。数据库URL、容器名及实例标记保存在忽略的`.env.test.local`，私有所有权记录在`.local/独立测试环境.json`。重复准备遇到已有配置会停止，不覆盖。

非quick检查拒绝当前副本的`.env`、`.env.local`、`.env.production`和`.env.production.local`，以免Next构建载入开发配置。核对实际库名、账号权限、实例标记、容器标签和端口后才进入数据库/构建检查。模型、通知及厂家读取的外发开关在检查进程中关闭。

## 三种检查范围

| 命令 | 实际范围 | 不能由此推定 |
|---|---|---|
| `pnpm check` | 类型与全部单元 | 数据库、浏览器、恢复已通过 |
| `pnpm check:core` | 类型/单元/环境/构建、固定核心数据库与HTTP浏览器子集、监测、归档、需求引用核对 | 全部模型及完整交付已通过 |
| `pnpm check:delivery` | 17步：类型/单元/环境/构建、旧版构建、全部数据库/HTTP浏览器、监测/归档/引用、本地检索与助手fixture、四组恢复、10分钟持续运行 | 真实农业效果、现场设备和生产灾备已通过 |

完整检查前先按原模型说明准备固定权重：

```sh
pnpm models:prepare
pnpm models:crop-prepare
pnpm check:delivery
pnpm check:report
```

恢复和升级只操作本轮随机测试schema。旧版本构建保存在`.local/发布旧版`，不会覆盖当前服务。完整检查包含构建，仍应使用独立副本。core不依赖模型文件；delivery缺模型时按阻塞记录，不能计完整通过。

## 运行状态与失败处理

同一副本只允许一轮检查，锁保存在`.local/检查锁.json`。第二轮会拒绝，避免竞争`.next`。正常结束自动释放；异常退出遗留锁时，`pnpm check:unlock`只清理本机已经不存在的进程对应锁，活进程或身份未知时拒绝。

每轮报告用原子替换保存，显示当前running步骤及耗时；完成后核对源码、锁文件、迁移和历史验收是否改变。源码变更、失败、跳过、缺前置或中断均不能签通过。报告和日志继续保存于`.local/验证记录/<运行编号>/`。

相同范围重新检查可使用：

```sh
pnpm check:core --retry-of <先前运行编号>
```

它创建新记录并重新执行该范围，不借用上一轮的成功结果。源码、平台、Node和测试实例一致且先前失败、随后成功时，会标出需要调查的不稳定线索；第一次失败保留，不能靠多次重跑抹掉。修复了代码后应开新一轮验收，不把它混成同版本偶发问题。

## 需求覆盖与公开摘要

`pnpm check:coverage`检查131个既有需求条目的代码、测试和执行记录，及项目文档相对链接；历史哈希变化、当轮未执行的映射分别报告。这里验证文件可追溯性，不声称每条需求已经有独立断言覆盖，也不关闭G依赖。原样保存的第三方模型卡内部链接属于上游仓库，单独列出，不改写原件。

`pnpm check:report`为各轮生成`公开摘要.json`和`公开摘要.md`。摘要只包含固定检查ID、状态、数字指标、提交与摘要等白名单字段；不复制命令、日志正文、私有路径、转储、凭据或业务原件。完整失败用例与复现命令仍在本机私有报告中。

GitHub工作流只上传这些白名单摘要，保存14天。PR/push默认core；手动选delivery或专用`quality-delivery-`验证分支执行完整范围。工作流使用只读仓库权限，不包含生产部署或分支保护修改。缺少OAuth的workflow授权时不能提交工作流，更不能记作远端成功。

## Linux冷安装

```sh
pnpm check:linux
```

默认使用Debian官方源；本地线路下载过慢时，可用`AGRI_APT_MIRROR=tuna pnpm check:linux`选择清华镜像，报告会记录选择。镜像入口只允许这两个选项，Debian签名校验保持启用；不会修改宿主软件源。参见[Debian镜像说明](https://www.debian.org/mirror/list)与[清华镜像使用说明](https://mirrors.tuna.tsinghua.edu.cn/help/debian/)。

要求当前副本已提交且无未提交文件。它克隆固定提交到新的私有目录，创建另一套测试容器，在固定Node22.15.0的Linux/amd64容器中全新安装依赖、浏览器并执行core。结束后停止自己创建的数据库容器；报告留在`.local/Linux冷安装/`。

Linux执行容器与自建测试数据库共享网络命名空间，检查器验证二者标签和网络关系。Docker套接字仅为本次已审代码的容器检查与隔离恢复使用，此工具不用于运行未经审阅的外部PR。Linux本机通过和GitHub远端通过分别记录，不能相互替代。

## 发布候选清单

```sh
pnpm release:manifest <完整交付运行编号>
```

要求完整17步通过，源工作区已提交，当前提交/源码摘要/构建与验收一致，并核对升级回退及10分钟报告。源码或构建变化后拒绝沿用旧验收。候选清单包含提交、源码/锁文件/迁移哈希、构建ID及配置项名称，不包含配置值。

清单仅证明该候选的工程条件，生产部署仍依赖G06实际环境与人员。纯文档后续提交不会改写旧清单；该清单继续指向实际验收的代码提交。不要把生产环境恢复目标填成本机工程耗时。

## 结束测试

```sh
pnpm test:stop
```

该命令核对容器ID和本轮所有权标签，只停止本副本创建的测试容器并删除对应连接配置。私有日志、报告和恢复备份继续保留，原应用服务与开发库不受该命令管理。
