# 一期持续备份与恢复

本轮补齐可执行的WAL归档、基础备份、归档健康和新目录PITR准备工具。真实NAS、专用生产集群和RPO/RTO尚未签认，现有开发数据库不自动启用这些配置。

依据PostgreSQL18官方[连续归档](https://www.postgresql.org/docs/18/continuous-archiving.html)及[pg_basebackup](https://www.postgresql.org/docs/18/app-pgbasebackup.html)。逻辑dump不能用于WAL回放；连续归档须保有基础备份起点以来的完整WAL链。低写入时也要限制归档间隔，本方案设置300秒，给15分钟目标留出上传与监控处理时间，不能因此宣称目标已达到。

1. 生产使用专用集群，先构建已有数据库镜像，再以`ops/Dockerfile.database-production`构建带Python归档工具的镜像。不要对现有含测试库的共用容器自动做集群级生产备份。
2. 将NAS真实独立卷挂载到数据库操作系统用户可写的`/var/lib/agri-backup`，权限0700。核对独立设备、故障域、容量、身份及访问恢复，手工在卷内保存0600的`独立备份卷核实.json`：`{"clusterId":"实际系统标识","independentStorageVerified":true,"evidence":"真实核实记录编号"}`。标识取专用集群`pg_controldata`，不能抄测试值。
3. 设置`WAL_ARCHIVE_ROOT`和`BACKUP_CLUSTER_ID`；将`ops/postgresql-production.conf`作为专用集群配置include，按其要求重启。归档脚本流式SHA复核、fsync、原子发布，遇同名异内容拒绝覆盖，失败返回非零；不清理pg_wal，不假报成功。
4. 在受控运维机准备0600的libpq service/password文件，用`PGSERVICEFILE`、`PGSERVICE`、`PGPASSFILE`引用，不把密码放命令行或Git。复制归档工具和对应版本PostgreSQL客户端。执行`python3 ops/base_backup.py --confirm-dedicated-cluster`；基础备份后运行pg_verifybackup并核对系统标识，不覆盖旧目录。
5. 每分钟执行`python3 ops/archive-health.py`，外部监控遇非零退出通知运维人员，另监测NAS空间、挂载和数据库pg_wal空间。只检查文件存在不够；本工具核最新归档SHA及数据库归档状态，仍需演练连续恢复。
6. 恢复时从已核基础备份向**新的绝对目录**运行`python3 ops/pitr_restore.py prepare '<基础备份目录>' '<新目录>' --target-time '<带时区时间>'`。脚本拒绝已有目标，重新pg_verifybackup，设置restore_command、recovery.signal和目标暂停。另启动同版本隔离实例验证；不自动停止或替换当前数据库。在确认业务、权限、恢复点与原件后由现场负责人切换。

归档路径和脚本安装路径使用不含空格/引号的固定路径。WAL工具不备份身份加密密钥、厂商凭据、配置、媒体原件或模型包；这些须按独立私有清单备份并核SHA，密钥另存且不进入报告。平台原件数据库关系、分块SHA和副本恢复由本轮隔离演练验证。

本机`python3 tests/acceptance/wal-archive.test.py`只验证重试、同名冲突、路径拒绝和私有目录，没有把临时目录称为独立NAS。正式验收须记录故障时间、最后可恢复事务、核心业务恢复时间、文件与权限校验、执行人；目标RPO≤15分钟、核心RTO≤2小时，以真实生产数据量与独立卷故障演练为准。
